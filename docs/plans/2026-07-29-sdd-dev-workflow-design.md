# SDD Dev Workflow 设计

## 背景

旧工作流把开发准备过程绑定到特定规范工具，并把需求整理、技术方案和代码实现分散在多个 Skill 中。新的目标是为开发者提供一个中性的单入口：从原始需求或 PRD 出发，先扫描工作区代码，再形成技术方案、实施计划和可执行任务。

## 决策

新增一个 `sdd-dev-workflow`，把原 `prd-ai-collab` 的需求结构化能力和 `project-writer` 的技术方案能力内嵌为两个阶段，不再把它们作为独立依赖迁入仓库。

工作流包含五个阶段：

1. 结构化需求；
2. 强制扫描工作区代码；
3. 编写技术方案；
4. 制定实施计划；
5. 拆分开发任务。

默认产物为：

```text
.sdd/<feature-id>/
├── requirements.md
├── design.md
├── plan.md
└── tasks.md
```

工作流默认在任务拆分处结束，不自动修改业务代码。后续实现由用户另行触发 `ai-pair-programmer`。

## 代码证据原则

技术方案前必须扫描工作区。单仓直接读取入口、调用链、数据模型、相似实现和测试；多仓优先复用已有 `app-scanner` 产物，必要时补充应用扫描。设计结论必须引用真实的相对文件路径与符号，未找到的内容应标记为未知或待确认。

## 追踪模型

四份产物使用统一追踪链：

```text
REQ-* / NFR-* -> DES-* -> PLAN-* -> TASK-*
```

这样可以从任一任务回溯到设计决策、需求和验收标准，也能识别需求覆盖缺口。

## 集成边界

- `brainstorming`：用于开放式探索和多方案取舍，可作为前置步骤，但不是硬依赖。
- `app-scanner`：多仓或多应用场景的上下文增强。
- `diagram-creation`：仅在图比文字更清楚时按需使用。
- `ai-pair-programmer`：在用户明确要求实现后承接 `tasks.md`，不属于本工作流默认范围。

## 验证

- 校验 Skill frontmatter、目录和引用文件；
- 运行仓库技能审计与安装 dry-run；
- 检查默认 profile、索引、工作流文档和功能分组；
- 扫描新目录中的特定工具绑定、私有地址、本机绝对路径和凭据；
- 使用模糊需求、已有 PRD、单仓、多仓和恢复流程五类提示做前向测试。

本设计文档不自动提交；是否提交由仓库维护者决定。
