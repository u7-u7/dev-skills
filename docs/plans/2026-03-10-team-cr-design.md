# Team CR Skill 设计文档

## 概述

**技能名称**：`team-cr`

**目标**：为多人协作的大型MR提供集体CR会议准备清单，自动过滤低价值问题，只输出需要团队讨论的高优先级问题。

**创建日期**：2026-03-10

---

## 痛点分析

当前集体CR存在以下问题：

1. **代码量大，效率差**：大型MR涉及大量代码，空指针等基础问题充斥其中，逐一讨论耗时
2. **缺乏优先级指引**：不知道哪些代码值得讨论，所有改动都看，时间不够用
3. **多人修改混乱**：多个作者的提交混在一起，难以识别各自的责任范围
4. **低价值问题多**：命名、魔法值、圈复杂度等问题现有工具即可检出，不需要会议讨论

---

## 设计目标

### 核心价值

- 自动过滤静态分析能检出的问题（命名、魔法值、圈复杂度等）
- 自动过滤基础runtime问题（空指针、类型转换、异常处理）
- 自动过滤纯格式问题和IDE警告
- 按风险等级（P0/P1/P2）+ 模块分组输出问题
- 为多人修改的代码标注作者归属

### 适用场景

多人协作的大型MR集体审查会议准备，包括：
- 多个作者参与的单个MR
- 发布前的整体质量把关
- 日常团队CR会议提效

---

## 过滤规则

### 自动过滤（排除项）

| 类别 | 具体排除项 | 理由 |
|:-----|:-----------|:-----|
| 静态分析 | 命名不规范、魔法值、圈复杂度过高 | SonarQube等工具自动检出 |
| 基础Runtime | 简单空指针风险、明显类型转换、基础异常处理 | IDE/编译器可检测 |
| 纯格式 | import顺序、换行、缩进、空行 | 格式化工具自动处理 |
| IDE警告 | 未使用变量、缺少import、过时API | IDE实时提示 |
| 主观建议 | 日志级别选择、注释风格、代码风格偏好 | 不影响功能，非CR重点 |

---

## 审查维度

仅保留高价值审查维度：

| 维度 | 检查重点 | 对应风险等级 |
|:-----|:---------|:-------------|
| **业务逻辑正确性** | 边界条件、数据一致性、幂等性、状态机正确性 | P0/P1 |
| **接口兼容性** | API契约变更、上下游影响、枚举扩展性 | P0/P1 |
| **架构与设计** | 分层合理性、职责边界、耦合度、事务边界 | P1/P2 |
| **性能风险** | N+1查询、RPC调用链、资源泄漏、热点路径 | P1/P2 |
| **并发安全** | 竞态条件、重复执行、事务隔离 | P0/P1 |
| **安全风险** | 越权访问、敏感数据、注入漏洞 | P0 |

**P0定义**：阻塞发布 / 数据损坏 / 严重安全漏洞
**P1定义**：影响可用性/可靠性的缺陷 / 明确的性能瓶颈
**P2定义**：架构隐患 / 可维护性问题

## 执行流程

### Step 1: 收集变更上下文

**1.1 获取变更范围**
```bash
git diff --stat base..head                    # 变更文件统计
git log --format="%H|%an|%ae|%s" base..head   # 提交列表与作者
git diff base..head --name-only               # 变更文件列表
```

**1.2 识别参与作者**
- 提取所有 committer 的 name 和 email
- 去重并按提交数排序
- 记录每个作者修改的文件集合

**1.3 聚合变更主题**
- 按目录结构分组（如 `order-service/`, `payment-service/`）
- 识别变更类型：新增/修改/删除
- 识别入口点类型：
  - HTTP：`@RequestMapping`, `@GetMapping`
  - RPC：`@DubboService`, `@Service`
  - Job：`@Scheduled`, `@XxlJob`
  - MQ：`@RocketMQMessageListener`

**1.4 构建调用链路映射**
- 从入口点出发，追踪调用的 Service/DAO
- 识别外部依赖（DB调用、RPC调用、缓存操作）
- 输出：入口点 → 服务层 → 存储层/外部依赖 的链路图

---

### Step 2: 逐文件审查与过滤

**2.1 读取每个变更文件的完整 diff**
```bash
git diff base..head -- <filepath>
```

**2.2 应用第一道过滤（静态分析类）**
对每个代码变更块：
- ❌ 排除：变量名/方法名/类名不规范
- ❌ 排除：魔法值（硬编码数字/字符串）
- ❌ 排除：圈复杂度警告（if/switch嵌套过深）
- ❌ 排除：方法/类长度警告
- ✅ 继续：非上述问题

**2.3 应用第二道过滤（基础Runtime类）**
- ❌ 排除：简单的 null 检查缺失（对象直接使用，未判空）
- ❌ 排除：明显的类型转换（如 `(List) Object` 无校验）
- ❌ 排除：基础异常处理（空 catch 块，但无业务逻辑）
- ❌ 排除：集合操作风险（未并发修改的迭代器修改）
- ✅ 继续：非上述问题

**2.4 应用第三道过滤（格式与IDE类）**
- ❌ 排除：import 顺序/多余 import
- ❌ 排除：换行/缩进/空行
- ❌ 排除：未使用变量/未使用 import
- ❌ 排除：@Deprecated 警告（除非影响功能）
- ✅ 继续：非上述问题

**2.5 应用第四道过滤（主观建议类）**
- ❌ 排除：日志级别选择（debug/info/warn）
- ❌ 排除：注释缺失/不完整
- ❌ 排除：代码风格偏好（如单行if是否加括号）
- ✅ 继续：非上述问题

---

### Step 3: 核心维度深度审查

对通过所有过滤的变更，按以下维度审查：

**3.1 业务逻辑正确性**
- 检查边界条件：null/空集合/0/负数/分页边界
- 检查数据一致性：DB/缓存/MQ的一致性
- 检查幂等性：重复执行是否安全
- 检查状态机：状态流转是否完整
- 输出：问题列表 + 证据行号

**3.2 接口兼容性**
- 检查方法签名变更：参数增减/类型变化
- 检查返回值变更：类型/结构变化
- 检查枚举变更：新增/删除枚举值
- 检查上下游影响：调用方是否同步修改
- 检查API扩展性：optional字段/默认值处理
- 输出：兼容性风险清单

**3.3 架构与设计**
- 检查分层边界：Controller/Service/DAO职责
- 检查耦合度：是否依赖不应依赖的层
- 检查事务边界：@Transactional 范围是否合理
- 检查职责单一：是否一个方法做太多事
- 输出：设计风险清单

**3.4 性能风险**
- 检查N+1查询：循环内DB/RPC调用
- 检查RPC调用链：是否有冗余/可合并的调用
- 检查资源泄漏：连接/流/线程池未关闭
- 检查热点路径：是否在热路径做重操作
- 输出：性能风险清单

**3.5 并发安全**
- 检查竞态条件：共享变量并发访问
- 检查重复执行：是否会导致重复写/扣款
- 检查事务隔离：并发事务是否会导致脏读/幻读
- 输出：并发风险清单

**3.6 安全风险**
- 检查越权访问：是否有权限校验
- 检查敏感数据：密码/密钥是否明文
- 检查注入漏洞：SQL/命令注入风险
- 输出：安全风险清单

---

### Step 4: 问题分级与作者归属

**4.1 问题分级（每维度独立判断）**

| 维度 | P0 | P1 | P2 |
|:-----|:---|:---|:---|
| 业务逻辑 | 数据不一致/状态错乱 | 边界条件缺失 | 逻辑冗余 |
| 接口兼容 | 破坏性变更无通知 | 兼容性风险未评估 | 扩展性不足 |
| 架构设计 | 事务边界错误 | 职责不清 | 可优化 |
| 性能 | 严重N+1/资源泄漏 | 热路径效率问题 | 可优化 |
| 并发 | 数据竞态/重复扣款 | 并发性能问题 | 可优化 |
| 安全 | 越权/注入/密钥泄露 | 敏感数据未脱敏 | 可优化 |

**4.2 作者归属（对每个问题）**
```bash
git blame -L <start_line>,<end_line> <file>
```
- 识别问题代码行的作者
- 关联到作者列表中的身份
- 输出：问题 → 作者 映射表

---

### Step 5: 生成报告

**5.1 首屏概览（一页纸）**
- 总体结论：可发/有条件/不可发
- 作者列表：参与人数 + 每人变更文件数
- 问题统计：P0/P1/P2 数量
- 模块统计：涉及模块 + 各模块问题数
- 讨论优先级：Top 3 必须讨论的问题

**5.2 按风险分组的问题清单**
- P0问题：每个问题一页表格
- P1问题：每个问题一页表格
- P2问题：简洁列表

**5.3 按模块分组的讨论指引**
- 每个模块一张表：涉及作者、问题数、讨论重点
- 讨论顺序建议：高风险模块优先

**5.4 作者归属表**
- 每个作者：需要参与讨论的问题清单
- 便于会议时分头讨论

## 质量门禁

### 执行前检查

1. ✅ 确认在 git 仓库中
2. ✅ 确认有可对比的分支/提交
3. ✅ 确认有代码变更（非空 diff）

### 执行中检查

1. ✅ 每个文件 diff 读取成功
2. ✅ git blame 可执行（用于作者归属）
3. ✅ 至少识别出一个入口点

### 执行后检查

1. ✅ 输出报告包含所有必需章节
2. ✅ P0/P1 问题都有明确证据（行号 + 代码片段）
3. ✅ 作者归属表完整
4. ✅ 过滤统计数字一致（过滤掉 + 保留 = 总检出）

### 特殊场景处理

- **无问题**：明确输出"未发现需要讨论的高优先级问题，建议快速通过"
- **仅 P2 问题**：输出"P2 问题较多，可选择性讨论或会后处理"
- **P0 过多（>10个）**：输出"P0 问题过多，建议先修复部分再上会"

### 禁止项

- ❌ 不得输出纯格式问题
- ❌ 不得输出命名/魔法值/圈复杂度问题
- ❌ 不得输出无证据的问题（必须引用具体代码行）
- ❌ 不得输出主观建议（如"建议增加日志"）
- ❌ 不得遗漏 P0 问题

```yaml
# Team CR - 集体代码审查

## 触发条件

用户触发词：
- `集体CR` / `团队CR` / `team cr`
- `多人CR` / `集体代码审查`
- `会议CR准备`

## 输入参数

| 参数 | 是否必需 | 默认值 | 说明 |
|:-----|:---------|:-------|:-----|
| `base` | 否 | `origin/main` | 对比基线 |
| `head` | 否 | `HEAD` | 对比目标 |
| `authors` | 否 | 自动识别 | 指定作者列表 |

## 与其他技能的区别

| 技能 | 输出重点 | 适用场景 | 是否依赖其他技能 |
|:-----|:---------|:---------|:-----------------|
| `team-cr` | 会议讨论清单，多人归属，模块分组 | 集体CR会议准备 | ❌ 完全独立 |
| `code-review` | 深度代码质量分析，10维度全量 | 个人开发/单PR深度审查 | ✅ 依赖 review-report |
| `full-review` | 完整审查 + 测试用例 | 发布前全面评估 | ✅ 依赖多个技能 |
| `author-final-review` | 单作者最终态审查 | 作者自查/发布前 | ❌ 独立 |
```
