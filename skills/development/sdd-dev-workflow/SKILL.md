# SDD 开发工作流

## 目标

把需求结构化能力和技术方案写作能力合并为一个入口，完成：

```text
原始需求 / PRD
  -> 结构化需求
  -> 工作区代码扫描
  -> 技术方案
  -> 实施计划
  -> 可执行任务
```

默认只生成开发准备文档，不修改业务代码，不执行任务。除非用户另行明确要求实现，否则在 `tasks.md` 收口。

其中，“结构化需求”内置原 `prd-ai-collab` 的通用能力，“技术方案”内置原 `project-writer` 的通用能力；不要求额外安装或跳转到这两个技能。

## 执行前记录

执行本技能前，先使用 `skill-usage-tracker` 记录：

```bash
bash scripts/skill-stats record --skill "sdd-dev-workflow" --context "需求到技术方案与任务拆分"
```

如果当前仓库没有统计脚本，说明情况并继续，不要阻塞主流程。

## 输出约定

优先遵循仓库已有的中性设计文档约定；没有约定时，使用：

```text
.sdd/<feature-id>/
├── requirements.md
├── design.md
├── plan.md
└── tasks.md
```

使用短小、稳定、由小写字母和连字符组成的 `<feature-id>`。如果同目录已有产物，先读取并判断当前阶段；未经用户授权，不覆盖已确认内容。

统一使用以下追踪关系：

```text
REQ-* / NFR-* -> DES-* -> PLAN-* -> TASK-*
```

## 阶段路由

先判断用户希望推进到哪一阶段：

| 用户意图 | 最远推进到 | 必须读取的已有产物 |
|---|---|---|
| 梳理需求、结构化 PRD | `requirements.md` | 原始需求或 PRD |
| 编写技术方案 | `design.md` | `requirements.md`、工作区代码 |
| 制定实施计划 | `plan.md` | `requirements.md`、`design.md`、当前代码证据 |
| 拆分开发任务 | `tasks.md` | 前三份产物、当前代码证据 |
| 完整开发准备 | `tasks.md` | 全部输入与工作区代码 |

用户要求“继续”“恢复”或目录中已有部分产物时，从最近一个质量门槛通过的阶段继续。先检查代码是否漂移，再决定是否需要更新下游文档。

## 阶段一：结构化需求

读取 [requirements-template.md](references/requirements-template.md)，把文本、文件或已有 PRD 归一为 `requirements.md`。

执行规则：

1. 保留原始需求中的编号、优先级、术语和验收条件；缺失时再使用 `REQ-001`、`NFR-001` 编号。
2. 明确背景、目标、非目标、范围、角色/场景、功能需求、非功能需求、约束和验收标准。
3. 使用可验证的验收表达；适合时采用“给定 / 当 / 那么”的结构。
4. 把模糊、冲突或缺失信息放入“假设与待确认问题”，不要把推测写成事实。
5. 如果信息足够支持安全推进，可带着显式假设继续；如果缺失会改变核心语义、数据安全或公共契约，先向用户确认。

需求阶段吸收了 PRD 结构化能力，但不要求额外调用另一个需求技能，也不绑定输入来源或协作平台。

## 阶段二：扫描工作区代码

技术方案开始前必须扫描工作区。即使用户提供了完整 PRD，也不能跳过。

### 单仓扫描

至少检查：

1. 仓库规则与状态：`AGENTS.md`、README、贡献指南、`git status`。
2. 项目类型与模块：构建清单、依赖文件、主要目录和配置。
3. 现有实现：入口、核心调用链、数据模型、持久化、外部依赖和错误处理。
4. 相似实现：可复用的接口、类、函数、组件、测试和发布模式。
5. 验证方式：已有测试、代码检查、类型检查、构建和运行命令。

优先使用 `rg --files`、`rg` 和项目原生工具进行只读检查。搜索结果要继续打开源文件确认，不能只根据文件名推断。

### 多仓或多应用扫描

出现以下任一情况时，先建立应用清单和依赖关系：

- 工作区包含多个应用仓库；
- 需求涉及多个端或跨应用调用；
- 当前会话无法确定完整影响范围。

优先读取已有 `app-scanner` 产物；没有可用产物时，使用 `app-scanner` 或执行等价的只读扫描。先按应用描述筛选候选，再读取候选应用的代码和依赖做深度确认。记录：

- 应用名称与职责；
- 匹配证据与置信度；
- 入口、接口、事件或数据依赖；
- 应用间依赖方向；
- 循环依赖和待确认边界。

### 代码证据门槛

每条关键结论至少记录以下信息：

| 字段 | 要求 |
|---|---|
| 文件路径 | 工作区相对路径 |
| 符号 | 类、函数、接口、配置键或数据结构 |
| 当前行为 | 从代码确认的事实 |
| 支持结论 | 该证据支撑的需求或设计判断 |
| 置信度 | 高 / 中 / 低及原因 |

找不到证据时写明“未发现”、已搜索范围和补救方式。禁止虚构文件、接口、表、事件或调用链。

## 阶段三：编写技术方案

读取 [technical-design-template.md](references/technical-design-template.md)，生成 `design.md`。

技术方案必须结合需求基线和代码扫描结果，至少覆盖：

1. 现状、问题和影响范围；
2. 总体方案与模块职责；
3. 关键流程和设计决策；
4. 接口、数据、事件、状态、配置或迁移设计；
5. 兼容性、安全、性能、可靠性和可观测性；
6. 测试策略、发布、回滚和风险；
7. `REQ/NFR -> DES` 追踪关系。

涉及新增或修改接口时，必须先找 1 至 3 个相似实现，并记录文件路径、符号、复用点、差异和兼容边界。确实没有相似实现时，写明搜索范围和风险控制。

只有在流程、交互或结构用图表达明显更清楚时，才使用 `diagram-creation` 补充流程图、时序图或架构图。图中的组件名称必须能映射回扫描到的应用或模块。

技术方案阶段吸收了工程技术方案写作能力，但不绑定特定行业、模板、技术栈或文档平台。

## 阶段四：制定实施计划

读取 [plan-template.md](references/plan-template.md)，生成 `plan.md`。

要求：

1. 按可交付里程碑组织，不按模糊时间段组织。
2. 每个 `PLAN-*` 关联一个或多个 `DES-*`，并有明确产物、依赖和退出条件。
3. 根据应用依赖和代码边界给出串行顺序与可并行项。
4. 把迁移、兼容、测试、发布和回滚放入对应里程碑，而不是留到最后一句带过。
5. 若发现循环依赖、设计缺口或代码漂移，把它列为阻塞项，不强行生成虚假的可执行计划。

## 阶段五：拆分任务

读取 [tasks-template.md](references/tasks-template.md)，生成 `tasks.md`。

每个 `TASK-*` 必须包含：

- 清晰动作和可观察产物；
- 目标应用、模块、文件或符号；
- 关联的 `REQ/NFR`、`DES` 和 `PLAN`；
- 前置依赖与可并行关系；
- 实现边界和完成标准；
- 具体验证命令或人工验证方法；
- 预期结果。

任务应小到可独立验证，但不要拆成没有交付价值的机械步骤。禁止使用“完善相关逻辑”“处理一下接口”等模糊措辞。路径尚未确认时，先创建有明确输出物的调查任务，不得伪造目标文件。

## 阶段质量门槛

按顺序检查：

1. **需求就绪**：范围内需求有唯一 ID、优先级和可验证验收条件。
2. **代码扫描完成**：关键现状与设计输入有真实文件或符号证据。
3. **技术方案就绪**：每个需求至少映射一个设计决策；高风险变更有测试和回滚策略。
4. **实施计划就绪**：依赖顺序可执行；每个里程碑有产物和退出条件。
5. **任务就绪**：每项任务可追踪、可执行、可验证，且需求覆盖无遗漏。

任一门槛未通过时，在文档中记录缺口、影响和下一步。只有缺口会改变核心方案或带来高风险时才暂停等待用户；其余情况可以保留显式假设继续生成草案。

## 完成时输出

向用户简洁说明：

- 生成或更新了哪些文件；
- 扫描了哪些仓库、模块和关键证据；
- 需求、设计、计划和任务的覆盖情况；
- 尚未确认的假设、风险或阻塞项；
- 工作流已在任务拆分处停止，尚未修改业务代码。
