# Team CR - 集体代码审查

## 触发条件

用户触发词:
- `集体CR` / `团队CR` / `team cr`
- `多人CR` / `集体代码审查`
- `会议CR准备`

## 输入参数

| 参数 | 是否必需 | 默认值 | 说明 |
|:-----|:---------|:-------|:-----|
| `base` | 否 | `origin/main` | 对比基线 |
| `head` | 否 | `HEAD` | 对比目标 |
| `authors` | 否 | 所有作者 | 指定要审查的作者（逗号分隔，如"张三,李四"） |

## 执行流程

### Step 0: 识别参与作者并询问选择

运行 `collect_changes.py` 和 `analyze_authors.py` 收集变更信息后，**向用户展示参与作者列表并询问选择**。

展示格式：
```
参与本次变更的作者：

序号   作者                          变更文件数
------------------------------------------------------------
1      张三                          15
2      李四                          8
3      王五                          12
------------------------------------------------------------

使用 AskUserQuestion 询问用户选择哪些作者（支持多选）。
```

### Step 1: 收集变更上下文

运行脚本收集变更信息：

```bash
# 设置变量
REPO="/path/to/repo"
BASE="${base:-origin/main}"
HEAD="${head:-HEAD}"
BRANCH_NAME=$(git branch --show-current)
OUTPUT_DIR=".doc/${BRANCH_NAME}"
WORKSPACE="/tmp/team-cr-$$"

# 创建工作目录
mkdir -p "$OUTPUT_DIR"
mkdir -p "$WORKSPACE"

# 收集变更
python3 skills/review/team-cr/scripts/collect_changes.py \
  --repo "$REPO" \
  --base "$BASE" \
  --head "$HEAD" \
  --output "$WORKSPACE/changes.json"

# 分析作者
python3 skills/review/team-cr/scripts/analyze_authors.py \
  --repo "$REPO" \
  --base "$BASE" \
  --head "$HEAD" \
  --output "$WORKSPACE/authors.json"
```

### Step 2: 询问用户选择作者

读取 authors.json，向用户展示参与作者列表，**使用 AskUserQuestion 询问选择哪些作者**。

用户选择后，将选定的作者列表传递给后续步骤。

### Step 3: 逐文件审查与过滤

对选定作者修改的文件：
1. 读取完整 diff：`git diff $BASE..$HEAD -- <file>`
2. 应用四道过滤规则
3. 对通过过滤的变更,按6个核心维度深度审查

### Step 4: 问题分级与作者归属

对识别出的问题：
1. 按 P0/P1/P2 分级
2. 按模块分组
3. 标注所属作者

### Step 5: 生成报告

按输出模板生成 markdown 报告到 `$OUTPUT_DIR/team-cr-YYYYMMDD-HHmmss.md`

## 质量门禁

### 基础质量检查

在进入集体审查前,必须通过以下质量门禁:

| 检查项 | 通过标准 | 失败处理 |
|:-------|:---------|:---------|
| 静态分析过滤 | ✅ 已排除所有命名/魔法值/圈复杂度问题 | 如有遗漏,重新应用过滤规则 |
| 基础问题过滤 | ✅ 已排除空指针/类型转换/异常处理等基础问题 | 要求作者会前修复 |
| 格式问题过滤 | ✅ 已排除格式/IDE警告问题 | 要求作者运行格式化工具 |
| P0问题数量 | ≤ 5个 | 超过则建议分专场或会前修复 |
| P1问题数量 | ≤ 15个 | 超过则延长讨论时间或分场次 |
| 可否上会 | ✅ 通过所有门禁 | ⚠️ 有条件通过 / ❌ 不建议上会 |

### 问题严重程度分级

#### P0 - 必须讨论（阻塞性问题）

**判断标准:**
- 业务逻辑错误:会导致数据不一致/状态混乱/金额损失
- 接口不兼容:破坏性变更,会影响现有调用方
- 并发安全缺陷:可能导致重复扣款/数据竞态
- 安全漏洞:越权访问/敏感数据泄露/注入风险
- 严重性能问题:会导致服务不可用/超时

**处理要求:**
- 必须在会议中讨论
- 需要明确修复方案和时间
- 建议指派负责人跟踪

#### P1 - 建议讨论（重要问题）

**判断标准:**
- 架构设计不合理:违反分层原则/过度耦合
- 性能风险:N+1查询/冗余RPC调用
- 接口扩展性不足:难以应对未来变化
- 事务边界不当:可能导致性能或一致性问题
- 非核心业务逻辑问题

**处理要求:**
- 建议在会议中讨论
- 可根据时间情况选择性讨论
- 记录问题供后续优化参考

#### P2 - 可选讨论（优化建议）

**判断标准:**
- 代码可读性问题
- 非关键性能优化
- 可维护性改进建议
- 最佳实践建议

**处理要求:**
- 时间充裕时可讨论
- 可通过代码评论方式反馈
- 不影响会议主流程

## 特殊场景处理

### 大规模变更（>50文件）

**场景:** 一次PR涉及大量文件变更

**处理策略:**
1. 优先识别核心变更文件(按目录/入口点分组)
2. 对非核心文件应用更严格的过滤规则
3. 生成模块级别的变更摘要
4. 建议分专场审查(按模块/功能)

### 跨模块变更

**场景:** 一次PR涉及多个服务模块

**处理策略:**
1. 识别跨模块调用链路
2. 重点检查接口兼容性
3. 按模块分组生成讨论清单
4. 标注依赖关系,建议讨论顺序

### 重构类变更

**场景:** 以重构为主的代码变更

**处理策略:**
1. 识别重构范围和目的
2. 重点关注重构引入的新问题
3. 适当降低对旧代码问题的关注度
4. 生成前后对比摘要

### 多作者协作

**场景:** 一次PR有多人提交

**处理策略:**
1. 分析每个作者的变更范围
2. 识别跨作者的代码冲突风险
3. 按作者生成问题清单
4. 标注需要协同讨论的问题

### 紧急修复

**场景:** 紧急hotfix,时间紧张

**处理策略:**
1. 仅关注P0级别的核心问题
2. 简化报告,快速输出关键信息
3. 标注需要后续完善的优化点
4. 记录技术债务供后续处理

## 问题归属机制

### 作者识别规则

使用以下机制识别问题代码的作者:

1. **主要作者:** 对文件变更最多的提交者
2. **代码行作者:** 通过 `git blame` 识别问题代码行的原始作者
3. **最近修改者:** 最后修改问题代码行的提交者

### 归属冲突处理

当一个问题涉及多行/多个作者时:
- 取最后修改者作为主要责任作者
- 在问题详情中标注涉及的所有作者
- 对有争议的问题标记为"需要讨论"

### 使用示例

**通过 AI 触发（推荐）:**
```
用户：帮我做集体CR
AI：[收集变更信息后]
    参与本次变更的作者：
    1. 张三 (15个文件)
    2. 李四 (8个文件)
    3. 王五 (12个文件)

    请选择要审查的作者？
用户：[选择张三、王五]
AI：[继续执行审查，只针对选定作者]
```

**命令行直接指定作者:**
```bash
# 直接指定作者列表
python3 skills/review/team-cr/scripts/run_team_cr.py --authors "张三,李四"

# 审查所有作者
python3 skills/review/team-cr/scripts/run_team_cr.py
```

**注意：**
- 通过 AI 触发时，AI 会**主动询问**你选择哪些作者
- 命令行模式可以省去交互，直接通过参数指定

**作者筛选说明:**
- `--authors` 支持逗号分隔的多个作者姓名
- 支持部分匹配（如 "张三" 可匹配 "张三 (zhangsan@example.com)"）
- 筛选后只会显示指定作者相关的：
  - 提交记录
  - 变更文件
  - 发现的问题
  - 模块和作者统计

**分步执行（调试用）:**
```bash
# Step 1: 收集变更
python3 skills/review/team-cr/scripts/collect_changes.py --repo . --base origin/main --head HEAD --output /tmp/changes.json

# Step 2: 分析作者
python3 skills/review/team-cr/scripts/analyze_authors.py --repo . --base origin/main --head HEAD --output /tmp/authors.json

# Step 3-5: 执行审查和生成报告（通过 run_team_cr.py 自动完成）
```

**输出位置:**
- 报告文件: `.doc/<branch-name>/team-cr-YYYYMMDD-HHmmss.md`
- 工作目录: `/tmp/team-cr-xxxxx/` (自动清理)

## 注意事项

1. **前置要求:**
   - 确保在git仓库根目录执行
   - 确保Python 3已安装
   - 确保有足够的git历史记录

2. **性能考虑:**
   - 大型仓库变更分析可能需要较长时间
   - 建议在变更范围合理时使用(<500个文件)

3. **结果解读:**
   - P0问题需要优先处理
   - 关注跨模块/跨作者的复杂问题
   - 质量门禁决定是否可以进入集体审查流程
